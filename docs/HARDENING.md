# Happow — security and optimization tasks

Oct 30, 2026

Things that are set loosely on purpose during development, or that work but could be tighter or faster. Each item says when it has to be done. The ones marked **Before launch** belong to M13 (launch readiness) at the latest. Add new items here as they come up; tick them off with a date and the PR.

## Security

- [x] **Sign-in code limits: stop resetting them by hand.** _Before launch._ Asking for a sign-in code is limited to 5 requests per hour per network (`auth.codeRequestsPerHourPerClient`) and 3 per day per email address (`auth.codeRequestsPerDayPerEmail`) in `config/app.json`. During development the owner was locked out after testing the Supabase redirect URLs, and both counters were cleared by hand in the live database (`rate_limits`, buckets `code-request` and `code-request-email`, 2026-10-30). The limits themselves weren't changed. Before launch: stop clearing them, check that 5 and 3 still fit real use, and decide whether staff need a way past them. **Done 2026-11-05 (owner):** raised to 10 per hour per network and 20 per day per address, no staff bypass (an admin can still generate a code in the panel). Stop clearing them by hand.
- [ ] **Previews use the live database.** _Before launch._ The Worker's **Previews Base** secrets are production's (Supabase URL and service-role key, salt, API keys), so anything done on a preview is real: sign-ins, submissions, approvals. Before launch: give previews their own Supabase project, or keep the service-role key out of previews. **Owner:** [LAUNCH.md](LAUNCH.md) §4.1.
- [ ] **Sign-in links may return to any preview.** _Before launch._ Supabase → Authentication → URL Configuration → Redirect URLs has `https://*-happow.krasnoroda.workers.dev/**`, so a link can land on any branch's preview. Before launch: narrow it to the final domain (and a preview pattern only if previews keep sign-in), together with the domain switch in M13. **Owner:** [LAUNCH.md](LAUNCH.md) §1.6, with the domain.
- [ ] **Sign-in codes are sent by hand.** _Before launch._ `auth.emailDelivery` is `manual`: the admin emails each code. Before launch: an email sender, then `emailDelivery` set to send automatically. **M13 slice E:** the sender is built (`auth.emailDelivery: "app"`, Resend); switching it on is [LAUNCH.md](LAUNCH.md) §1.4–1.5.
- [ ] **Biletyna's terms.** _Before launch._ The source was switched on (2026-10-30) after a check of robots.txt and its terms page, which didn't show the full terms. Before launch: read the full terms, or ask Biletyna, and record the answer in its `termsNotes`. **M13:** listed by `pnpm launch:check` through the source's `beforeLaunch`.
- [x] **Account feed addresses are checked only when added.** _Soon._ `POST /api/me/feeds` refuses private addresses (`checkPublicUrl`), but the ingest job fetches the stored address later without checking again, so a name that later points to a private address would be fetched. Also: no size limit on a feed's file. Fix: check the address again before each fetch, and cap the download size, as the crawler does for pages. **Done 2026-11-05 (M13 slice F):** every fetch and redirect is checked with `checkPublicUrl`, and a feed is capped at 2 MB (`fetchPublicText`).
- [x] **Previews and the cron.** _Check._ Cloudflare doesn't run Cron Triggers on previews, so a preview never ingests or saves metrics. Keep it that way: no `triggers` under `previews` in `wrangler.jsonc`. **Done 2026-11-05 (M13):** a test (`launchItems`) fails if `wrangler.jsonc` gives previews triggers.

## Optimization

- [ ] **Reminders per cron tick are capped for the Workers Free plan.** _Before reminders are widely used._ Sending one web push (encryption and VAPID signature, M10 slice E) takes about 1.5 ms of CPU (measured in Node, 2026-11-04). A Free-plan tick has 10 ms, shared with the ingest check and metrics, so `reminders.maxPerTick` in `config/app.json` is 6: more than 6 due in one tick go 15 minutes later, so they can arrive late. On Workers Paid (30 s of CPU) raise it to 200 or more. **Owner:** [LAUNCH.md](LAUNCH.md) §4.2 (M7 follow alerts are capped the same way, `follows.alerts.maxPerTick` 3).
- [ ] **Preview images need more CPU than the Workers Free plan allows.** _Before sharing goes live._ Drawing one shared-link preview image (M9 slice B, `/e/<id>/preview.png`) takes about 60 ms of CPU once resvg is loaded, and ~150 ms on a fresh isolate (measured in Node, 2026-10-30). Workers Free allows 10 ms per request, so on Free some first renders will be cut off: the link still previews with its title and time, but without the picture. Each image is drawn once per event version and then served from the edge cache. Fix: Workers Paid ($5/month, 30 s of CPU), or draw the images in the ingest job and store them (R2). Also: the Worker bundles two full Inter fonts (~680 KB); subsetting them to Latin would cut the bundle by about half a megabyte. **M13 slice F:** the two Inter fonts are subset to Latin, Latin Extended-A and punctuation (680 KB → 127 KB). The CPU part stays: Workers Paid, [LAUNCH.md](LAUNCH.md) §4.2.
- [ ] **The daily ingest run is long.** _When minutes run short._ Ingest runs were cut to about two a day (2026-10-30), but the daily one takes about 40 minutes, half of it the city portal: 120 event pages at the crawler's 5 s per request (10 min, kept for politeness) plus ~10 min for geocoding and writing ~640 events. Measure where the other 10 minutes go (geocoder cache hits vs Nominatim at 1 s, database round trips from the GitHub runner) before changing anything; fewer followed pages or a second region would change the budget. **M13 slice C** cuts repeat work (conditional requests, unchanged pages, event pages far ahead not refetched); measure again after a week of runs.
- [x] **Feed import geocodes events it already has.** _Soon._ `packages/ingest/src/feeds.ts` geocodes each feed event before it knows whether `feed_import` will take it, so every run asks the geocoder again for events imported earlier (the cache softens it, but each still costs a lookup). Fix: work out the event's key first and skip known keys, for example by reading the feed's known keys once per run. **Done 2026-11-05 (M13 slice F):** known keys are read once per feed and skipped before geocoding.
- [x] **Coverage counts each district twice.** _When regions grow._ `coverage()` (migration 21) checks every live event against every district polygon, once for the totals and again per category. Fine for 48 districts and a few hundred events a week. With more regions or events: count per district once (a join with `st_covers`, grouped), and only then split by category. **Done 2026-11-05 (M13 slice F, migration 28):** one pass per district, categories split from it; private events no longer counted.
- [ ] **Account card reads every contribution at once.** _When accounts grow._ `contributions_get` sums counts and thanks for up to 200 of an account's events on every opening of the card. For very active accounts: keep running totals, or page the event list.
- [x] **The district goal is asked live.** _Check._ `district_goal` runs on every empty reach (after moves of about 100 m), uncached. If it shows in the database's load: cache it at the edge per district and weekend, like the area cache. **Done 2026-11-05 (M13 slice F):** the app keeps each answer per ~100 m and weekend for one data step, so walking back and forth asks once.
